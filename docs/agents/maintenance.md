# 制度檔維護協議

> 讀者：未來要更新 CLAUDE.md、docs/、memory 的任何模型。
> 核心原則：**制度檔的價值在於被信任；寧可少改，不可改錯。**

## 一、改動權限分級

| 動作 | 權限 |
|------|------|
| 修正已查證的事實錯誤（路徑、指令、行號）並註明日期 | 可自行改 |
| 在 memory 新增踩坑教訓（feedback 類） | 可自行改 |
| 更新 `docs/DATA_RULES.md` 的賽季性內容（新賽季 H2H 表等） | 可自行改，但要附資料來源 |
| 修改 CLAUDE.md 的政策段（部署政策、語言規定、裁決順位） | **先問使用者** |
| 修改 `dispatch.md` 的升降級路徑、`judgment.md` 的判準本文 | **先問使用者**（可自行在判準下追加新的正反例） |
| 刪除任何制度檔或大段內容 | **先問使用者** |
| 改 `docs/agents/_backup/` 下的備份 | 永遠不改 |

## 二、改動前的固定動作

1. 先讀要改的檔案全文（不是只讀要改的段落）。
2. 用 Grep 查同一內容有沒有出現在其他檔（CLAUDE.md / docs/ / memory）——有就一起改或改成引用，**不要留下第二份會分岔的副本**。
3. 改完在該段落尾註記 `（2026-XX-XX 更新：原因一句話）`。

## 三、踩坑教訓寫回哪裡

| 教訓類型 | 寫到 |
|----------|------|
| 使用者糾正了工作方式 | memory 新檔（type: feedback，含 Why 與 How to apply）＋ MEMORY.md 加一行索引 |
| 專案事實變了（換季、部署方式變更） | 對應的 docs/ 檔（DATA_RULES / SEASON_WORKFLOW），memory 若有舊說法要同步勘誤 |
| 某條判準誤導了你 | `judgment.md` 該條下追加反例；若判準本身要改，先問使用者 |
| 派工失敗的模式 | `dispatch.md` 第七節「派工紅線」追加一條（附日期） |

**勘誤格式**（過時內容不直接刪，先標記一個版本週期）：
```
~~舊說法~~ — 2026-XX-XX 查證：實際是 …（證據）
```
下次再碰到該檔時，若勘誤已存在超過一個月，可把刪除線內容整段移除。

## 四、精簡時機

- CLAUDE.md 超過 **80 行** → 過長，把細節下放到 docs/ 專門檔，只留路由。
- 單一制度檔超過 **150 行** → 檢查是否混了兩個主題，拆檔。
- MEMORY.md 索引超過 **20 條** → 跑 `anthropic-skills:consolidate-memory` skill 合併重複、清過時。
- 精簡＝搬家或合併，**不是删資訊**；刪資訊要先問使用者。

## 五、每次賽季轉換時的制度體檢（掛在 Playbook A 執行時順做）

1. `docs/DATA_RULES.md` 的賽季性表格（H2H、賽季碼）更新了嗎？
2. CLAUDE.md 關鍵路徑表的檔名（`*_2526.json` → 新賽季碼）對了嗎？
3. memory 裡有沒有寫死舊賽季的說法需要勘誤？
