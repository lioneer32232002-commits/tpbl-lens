# 判斷力 Rubric

> 讀者：任何等級的模型，特別是 Sonnet/Haiku。每條判準附一個正例、一個反例，例子都取自 tpbl-lens 的真實情境。
> 原則：**判斷不了的時候，照著判準的字面執行就好**，不要自由發揮。

## 1. 何時該升級模型（或收回主對話）

**判準**：同一子任務錯兩次、或發現任務需要「取捨」而不只是「執行」（要在多個都對的做法之間選一個），就升級。

- ✅ 正例：派 Haiku 批次把 7 個球隊 JSON 加一個欄位，它把 `formosa_2526.json` 的結構弄壞了 → 不重派，改 Sonnet 或收回自己做。
- ❌ 反例：Haiku 弄壞一次，換個措辭再派 Haiku 一次，又壞，再換措辭……（重試不是修復，同樣的手只會產生同樣的錯）

## 2. 何時算「真的完成」

**判準**：三項全滿足才算完成——(a) 驗收條件逐條打勾；(b) 有可展示的證據（指令輸出、preview 截圖、read-back 結果）；(c) **若本次有改動檔案**，改動已依部署政策處理（commit 含 dist/，push 完成）。缺一項就不要說「完成」。純查詢／研究任務與 subagent（templates 規定不碰 git）只需滿足 (a)(b)。

- ✅ 正例：改了 `js/championship.js` → `python build.py` exit 0 → preview 開 8765 確認冠軍頁渲染正常 → commit（含 dist/）→ push → 回報「完成，證據：…」。
- ❌ 反例：「我已經修改了 championship.js，應該可以正常顯示了」——沒跑 build、沒開 preview。「應該可以」＝未完成。

## 3. 何時該停下來問使用者

**判準**：符合任一條就問——(a) 對外且立即生效（wrangler deploy）；(b) 破壞性且難復原（刪 worktrees、改歷史、覆蓋非自己建立的檔案）；(c) 兩份權威來源矛盾且查實際狀態也無法裁決；(d) 任務範圍要變（使用者要 A，做到一半發現其實該做 B）。

- ✅ 正例：發現 13 個舊 worktree 想清理 → 屬破壞性，先問。
- ❌ 反例：改一行 CSS 也停下來問「請問我可以開始了嗎？」——可逆、範圍內的事直接做，問了反而浪費使用者時間。

## 4. 什麼訊號代表方向錯了，該換路而非重試

**判準**：出現任一訊號就停止目前路線，退回上一個決策點——(a) 修 A 壞 B、修 B 又壞 A（打地鼠）；(b) 為了讓方案成立，需要的「特例處理」超過兩個；(c) 花掉的 token/時間已超過重新來過的成本；(d) 發現自己在跟工具打架（例如硬要在主對話 parse 大 JSON）而不是在解問題。

- ✅ 正例：想在前端 JS 重算系列賽統計，越寫越多特例 → 停，改回「資料在 `compute_champ_todate.py` 算好、前端只渲染」的既有架構。
- ❌ 反例：同一個 regex 改第五版還在錯，繼續改第六版——這是打地鼠訊號，該換方法（改用 python 腳本處理或換資料源頭）。

## 5. 品質底線怎麼驗

**判準**：每種產出對應固定驗法，驗不過就不出手——
- Python 改動：`python build.py` exit 0；有對應測試就 `pytest`
- 前端改動：preview（port 8765）實際打開該頁，用 snapshot/console 檢查，不是「看程式碼覺得對」
- 資料檔改動：用 `python -c` 抽改動欄位確認值正確、`json.load` 不報錯
- 文件改動：派 fresh agent read-back（只給驗收條件），或至少自己重讀一次檢查路徑與指令可執行
- ✅ 正例：改 `data/championship_2526.json` 後跑 `python -c "import json;json.load(open('data/championship_2526.json',encoding='utf-8'))"` 確認合法。
- ❌ 反例：手改 JSON 後直接 commit，被尾逗號弄掛整個冠軍頁。

## 6. 模糊題與品味判斷（誠實條款）

**判準**：以下類型的題目，流程與驗證救不了，弱模型不要硬撐——視覺設計好不好看、文案語氣對不對、分析洞見有沒有價值、pitch 素材有沒有說服力。遇到時：(a) 給 2–3 個具體選項讓使用者挑，附各自 trade-off；(b) 或明說「這題我的判斷不可靠，建議你看一眼」。已有既定品味規則的要先查：圖表圖例規則在 memory（彩色文字、不用圖示符號）。

- ✅ 正例：OG 圖配色不確定 → 做兩版縮圖讓使用者選。
- ❌ 反例：自行決定「這個分析角度球團一定喜歡」然後大改頁面結構——pitch 的品味判斷屬於使用者。
