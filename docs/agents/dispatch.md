# 模型調度守則

> 讀者：主對話的模型（日常為 Opus，有時是 Sonnet）。目的：決定「自己做還是派工」「派給誰」「怎麼派」「錯了怎麼辦」。
> 本守則按 tpbl-lens 的實際規模調整過：這是單人小專案，**過度派工比不派工更浪費**，先看任務分級。

## 一、任務分級：先判斷要不要派工

| 級別 | 判準 | 做法 |
|------|------|------|
| **S（直接做）** | 改動 ≤3 個已知路徑的檔案；或跑固定流程（build→commit→push、Playbook C-2 更新冠軍頁） | 主對話直接做，**不要派工**。派工的來回溝通成本高於任務本身 |
| **M（派搜尋）** | 需要掃 >3 個檔案找東西、查外部網頁、盤點現況 | 派 **Explore**（唯讀）或 general-purpose，主對話只收結論 |
| **L（派實作＋驗收）** | 新功能、跨 js/pages/python 多層的改動、歷史賽季重構 | 先派 **Plan** 或自己規劃 → 拆小任務逐一實作 → 每個任務完成後派 fresh agent 驗收（見「海豹小隊」記憶） |

**判斷不了級別時：當 S 做，做到第 4 個檔案還沒完就停下來，升級成 L 重新規劃。**

## 二、可用的 subagent 類型與模型（2026-07-03 實查本環境）

| agentType | 用途 | 何時用 |
|-----------|------|--------|
| `Explore` | 唯讀搜尋，會自己節制讀檔量 | 一切「找東西、盤點、確認現況」 |
| `Plan` | 架構規劃，回傳步驟計畫 | L 級任務開工前 |
| `general-purpose` | 全工具，可改檔 | 實作型派工、批次修改 |
| `claude-code-guide` | 查 Claude Code/API 用法 | 對 harness 功能有疑問時，別憑記憶回答 |

**model 參數**：Agent 工具可指定 `sonnet` / `opus` / `haiku`（`fable` 在 2026-07 的 schema 裡存在，但不保證長期可用，不要依賴它）。省略 model = 繼承主對話模型，**預設就省略**。只在兩種情況指定：
- 機械性批次工作（套用已驗證的固定模式、格式轉換、逐檔重複操作）→ 指定 `haiku`
- 主對話是 Sonnet 而任務是高風險判斷（見 judgment.md）→ 指定 `opus`

**誠實註記**：主對話自己的 effort／模型由使用者在 harness 設定，模型無法自行調整；Agent 工具也沒有 effort 參數。「用最高 effort」這類要求只能由使用者在設定裡做。

## 三、派工三件套（每個派工 prompt 必含，模板見 templates.md）

1. **目標與動機**：做什麼＋為什麼（讓 subagent 能在細節上自行取捨）
2. **驗收條件**：可檢查的具體條件（「build.py 跑過且 exit 0」「回報含 檔案:行號」），不是「做好做滿」
3. **回報格式**：規定回報的結構與長度上限

## 四、回報合約（subagent 端）

- 只回**結論**與 `檔案:行號`，不貼大段程式碼或檔案內容
- 長產物（報告、清單）落檔到 `scratchpad` 或 `docs/`，回報只傳路徑
- 回報長度給明確上限（例：150 行以內）
- 派工 prompt 一律繁體中文（見 CLAUDE.md 語言規定）

## 五、升降級路徑（以 Opus 為日常主模型）

- **Haiku 派工錯一次** → 不重試，直接改派 Sonnet 或收回主對話自己做
- **Sonnet 派工同一子任務連錯兩次** → 帶完整失敗軌跡（原 prompt、兩次錯誤輸出、錯在哪）收回 Opus 主對話處理
- **Opus 主對話同一問題連錯兩次** → 沒有更高一級可升。停下來：把失敗軌跡整理成摘要，向使用者說明卡在哪、已試過什麼、建議的兩條路。**不要第三次盲試**
- **降級**：某個模式已被解出並驗證（例：某類頁面的固定改法），批次套用時降 Haiku/Sonnet 逐檔執行
- **重試上限**：同一件事最多兩輪，第三輪必須換方法或換人（含問使用者）

## 六、驗證不自驗

寫的人不驗自己的產出。分三類：

| 產出類型 | 驗法 |
|----------|------|
| 文件/資料檔 | 派 fresh-context agent read-back：只給驗收條件不給過程，讓它讀檔回答「是否滿足」 |
| 程式碼 | 實跑：`python build.py` exit 0、`pytest`（tests/ 存在）、前端用 preview 工具（launch.json 已設 8765）截圖或 snapshot |
| 高風險判斷（部署、刪東西、資料勘誤） | 第二意見：派一個 agent 以「找出這個結論的錯誤」為目標審一次，或直接問使用者 |

**驗證 agent 的 prompt 不要透露「我覺得已經做完了」**——只給驗收條件，避免誘導。

## 七、本專案特有的派工紅線

- 不要派 agent 去讀 `dist/`（build 產物）或整檔讀 `data/*.json`（讀法見 `docs/DATA_RULES.md`）
- `docs/superpowers/plans/` 下的計畫檔是**歷史紀錄**，大多已實作，不要派 agent 去「執行」它們
- 部署（wrangler）不可委派給 subagent 自動執行——那是要先問使用者的動作
